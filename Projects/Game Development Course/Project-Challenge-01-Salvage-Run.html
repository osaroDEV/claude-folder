SALVAGE RUN — Station Kepler

Build a complete arcade game from an empty folder. Nothing here is copied from any demo you've seen in class — you have to think it through and write it yourself.

Sessions 1 → 12 ≈ 4–6 hours Spread over 2 weeks 9 build stages Difficulty: hard, but every piece is something you already know

Why this project exists

  • Every single thing you've learned in twelve sessions is required to finish it — miss one and the game won't work.
  • Nobody hands you the code. You get a specification, like a real developer does, and you build to it.
  • It is the first thing you'll have made that is genuinely yours — not a demo you followed along with.
🚫 The one big rule
Do not open any of the class demos while you build this. Not the bouncing ball, not the driving square, not the target game, not the falling blocks. Your own notes are fine. The course pages for explanations are fine. Copying working game code from them is not — it turns a project into typing practice. If you're stuck, use the Stuck? panel inside each stage. Those panels give you a nudge and never the answer.

📡 The mission brief

A cargo hauler has broken apart just outside Station Kepler. Its cargo pods are drifting all over the sector, and so is a field of rock debris. You are the pilot of the station's little salvage tug.

You have 60 seconds. Two jobs, at the same time:

  • Left hand on the arrow keys — fly the tug around and collect the drifting cargo pods.
  • Right hand on the mouse — rocks glow orange when they go unstable. Click an unstable rock to vaporise it before it reaches the station.

The station core sits in the middle of the screen with a shield. Every rock that touches the core takes shield away. Unstable rocks take three times as much. When the shield hits zero, it's over — and the timer running out ends it too.

📋 The specification

This is the part you must build to. Read it twice before you write a single line. Treat anything in bold as a hard requirement.

The four kinds of thing on screen

ThingShape & dataBehaviour
Tug
(you)		 Rectangle
{ x, y, w, h, speed }		 Moves in all four directions with the arrow keys. Clamped so no part of it ever leaves the canvas. Diagonal movement must work (hold two keys).
Pods
(the loot)		 Rectangles in an array
{ x, y, w, h }		 8 per wave at random positions. Never spawn one inside or touching the core. Collected when the tug overlaps it → +10 score and the pod is removed from the array. Empty array = wave cleared → +50 bonus, next wave spawns, and one more rock joins the field.
Rocks
(the danger)		 Circles in an array
{ x, y, r, vx, vy, unstable }		 Start with 3. Each drifts by its own velocity and bounces off all four walls. Every 5 seconds one random rock turns unstable (draw it a different colour). Rocks pass straight through the tug and the pods — they only care about the core.
Core
(what you defend)		 Circle
{ x, y, r, shield }		 Sits dead centre, does not move. Shield starts at 10. A rock touching it costs 1 shield, or 3 if that rock was unstable. The rock is then removed and a fresh one spawns at a random edge. Shield draws as a number inside the core.

Mouse rules

  • Clicking an unstable rock vaporises it: +25 score, rock removed, a fresh normal rock spawns at a random edge.
  • Clicking a normal rock costs you -5 score. (So no wild clicking. Aim.)
  • Clicking empty space does nothing.
  • Clicks must land exactly where you clicked — no offset. You know why.

Game state and controls

  • 60-second timer, counting down, shown in the HUD.
  • P pauses and unpauses. While paused, nothing moves, but the screen still draws and shows the word PAUSED.
  • R restarts the whole game from scratch, at any time.
  • Game ends when the shield reaches 0 or the timer reaches 0. On the end screen show the final score and which of the two ended it.

HUD (one line, top-left)

Score: 120   Wave: 2   Pods: 5   Shield: 8   Time: 41

Built by joining text and numbers together — not five separate fillText calls with hardcoded words in random places.

🔑 Two rules about how the code is written, not what it does

1. Every tuning number lives in one place. At the very top of your JavaScript, a block of const settings: tug speed, pod count, rock count, shield amount, the timer length, score values. Nothing further down the file may contain a "magic number" you'd want to tweak. I should be able to make the game twice as hard by editing five lines at the top.

2. update() stays small. Aim for about 12 lines. It should read like a list of instructions — movePlayer(), moveRocks(), checkPodPickups(), checkCoreHits() — with the actual work living inside named functions. If update() is 60 lines long, you haven't finished; you've just stopped.

Functions you are required to write

These specific ones must exist, must take parameters, and the first four must return a value:

randomBetween(min, max)      → returns a number between min and max
distance(ax, ay, bx, by)     → returns the straight-line distance between two points
rectsOverlap(a, b)           → returns true or false
circlesOverlap(a, b)         → returns true or false
makeRock()                   → returns a brand-new rock object, ready to push into the array
spawnWave()                  → fills the pods array with a fresh wave
resetGame()                  → puts every variable back to its starting value
💡 Watch what happens with distance
You will call that one function for three completely different jobs: deciding whether a click hit a rock, deciding whether a rock hit the core, and keeping new pods away from the core. Write it once, use it three times. That's what "don't repeat yourself" actually feels like in practice.

🧭 How to build it: nine stages

Do not try to write the whole thing and then run it. That way lies pain. Build one stage, run it, make sure it does what "Done when" says, and only then start the next one. Each stage is roughly 20–40 minutes.

Tick a stage off as you finish it — the bar at the top fills up.

STAGE
0

Set up the studio

Session 1Session 2Session 3
Goal: a proper three-file project that opens in the browser and looks like a real game page — before any game exists.
  1. Make a new folder called salvage-run in your projects folder. Open it in VS Code as a folder, not as loose files.
  2. Create three files inside it: index.html, style.css, game.js.
  3. In index.html, write the page skeleton by hand. It needs: a real <h1> title, a <canvas> that is 720 wide and 480 tall with an id, and a <p> underneath explaining the controls to the player.
  4. Link the stylesheet in the <head>. Link the script at the end of the body with <script src="game.js"></script>.
  5. In style.css: dark page background, centre the canvas horizontally, give the canvas a visible border and rounded corners, choose a font for the page, and use margin and padding deliberately so nothing is squashed against anything else.
  6. In game.js, write one line: console.log("Salvage Run booting…");
  7. Open the page in your browser, open DevTools, and confirm that message is in the Console and there are no red errors.
⚠️ Set the canvas size in the HTML, not the CSS
width and height go on the <canvas> tag as attributes. If you set the size in CSS instead, the canvas gets stretched like a blown-up photo and every coordinate you calculate all project long will be subtly wrong. This is a bug that is genuinely horrible to find later.
Stuck?

If the console message doesn't appear, the script tag isn't finding your file. Check the spelling of the filename, check it's in the same folder, and look at the Network or Console tab for a 404.

If the canvas is invisible, that's normal — it's transparent until you give it a background or a border in CSS. That's exactly why step 5 asks for a border.

Done when the page shows a title, a bordered empty canvas centred on a dark background, and a controls line — and the Console shows your boot message with no errors.

STAGE
1

Settings, the core, and text on the canvas

Session 2Session 4Session 5
Goal: a settings block at the top of the file, the station core drawn in the exact middle, and a HUD line built from variables.
  1. Grab the canvas and its 2D context. Store the width and height in constants — you'll use them constantly and typing canvas.width forty times is miserable.
  2. Write the SETTINGS block: constants for tug speed, pods per wave, starting rocks, starting shield, round length in seconds, and the four score values (pod, wave bonus, vaporise, wrong click).
  3. Create your changing variables with let: score, wave, and the two booleans paused and gameOver.
  4. Create the core object at the exact centre of the canvas, with a radius and a shield value taken from your settings.
  5. Write a function drawCircle(c, colour) that draws any circle object, and drawRect(r, colour) for any rectangle object. Use them for everything from here on.
  6. Draw the core once, and draw the HUD line by joining your variables into one string.
🎯 Why const for some and let for others
A setting is decided once and never changes while the game runs — that's const. The score changes constantly — that's let. Getting this right is not fussiness: const means the computer will stop you from accidentally overwriting something important.
Stuck?

Nothing drawing at all? Two usual suspects: you didn't get the context (getContext("2d")), or your script is running before the canvas exists on the page — which is exactly why the script tag goes at the end of the body.

For the HUD, remember that a number joined onto a string becomes text automatically. Build the whole line as one string in a variable first, then draw that variable. Easier to debug.

Done when a circle sits in the dead centre of the canvas and a line of text at the top-left reads Score: 0 Wave: 1 Pods: 0 Shield: 10 Time: 60 — every number coming from a variable, none of them typed into the string by hand.

STAGE
2

The engine: update, draw, loop

Session 8Session 5Session 6
Goal: the thing is alive. Sixty frames a second, forever, with a working pause.
  1. Split your drawing code into the three-function skeleton you know: one that changes things, one that paints things, one that runs both and asks for the next frame.
  2. Make the very first line of the painting function wipe the canvas.
  3. Add a frame counter that goes up by one every frame, and work the remaining time out from it. Sixty frames is one second.
  4. Add the pause: a keydown listener on the document for the P key that flips the paused boolean. Then make the updating function do nothing at all while paused — but keep drawing, and draw the word PAUSED in the middle.
  5. Do the same for R, calling a resetGame() function. It can be nearly empty for now; you'll fill it in as you add things.
🔑 The neatest way to pause
You do not need to wrap your whole update function in a giant if. The first two lines can simply be a check that leaves the function early when paused or when the game is over. That's a guard — one of the most useful three-line patterns in programming, and you'll use it in every game you ever write.
Stuck?

Timer showing something like 59.98333? You need to chop the decimals off — there's a maths function for rounding down.

Pressing P flickers wildly between paused and unpaused? You've probably put the flip inside something that runs every frame instead of inside the key event. The event fires once per press; the loop fires sixty times a second.

Nothing at all happens on key press? Remember from Session 10 that key events go to whatever has focus. For whole-game keys like pause and restart, listening on document is the simpler choice.

Done when the timer counts down from 60 in real seconds, P freezes it with PAUSED on screen and unfreezes it, and R sets it back to 60.

STAGE
3

Fly the tug

Session 10Session 6Session 4
Goal: a rectangle you can fly around in all directions, that cannot escape the screen.
  1. Create the tug object with position, size and speed (speed from your settings).
  2. Set up the "which keys are held" record with a keydown and a keyup listener. Stop the arrow keys from scrolling the page.
  3. Write moveTug(): four separate checks, one per direction, each moving the tug by its speed. Call it from your update function.
  4. Clamp the tug so no part of it leaves the canvas — remember that its x is its left corner, so the right-hand limit isn't the canvas width.
  5. Draw the tug using your drawRect helper.
⚠️ Do not move the tug inside the key event
You know why from Session 10 — the operating system's key-repeat makes it stutter. The listeners write down true and false, and nothing else. The loop does the moving.
Stuck?

Only one direction works at a time when you hold two keys? You've used else if between the four checks. They must be four independent checks.

The tug slides off the right side by exactly its own width? You clamped against the canvas width instead of the canvas width minus the tug's width.

Key names are case-sensitive and spelled precisely, and a wrong spelling fails silently. If a direction does nothing, print the key name to the console and read what the browser actually calls it.

Done when you can fly smoothly in eight directions (including diagonals), and pressing hard into any corner parks the tug perfectly against both edges with nothing hanging off.

STAGE
4

Cargo pods: arrays, loops and collecting

Session 7Session 12Session 5
Goal: eight pods scattered around, and a tug that collects them by flying into them.
  1. Create an empty pods array and write spawnWave(), which uses a loop to add the right number of pods at random positions.
  2. Two spawn rules: a pod must be fully on screen, and it must be at least 90 pixels from the centre of the core. Use your distance() function for the second one, and simply pick again if the spot is no good.
  3. Draw every pod with a loop over the array.
  4. Write rectsOverlap(a, b) — the four-comparison test — and use it in checkPodPickups() to test the tug against every pod.
  5. On a pickup: add to the score and remove that pod from the array.
  6. When the array is empty: award the wave bonus, add one to the wave number, spawn a new wave, and log to the console which wave has started and how many pods it has.
🐛 The trap in this stage — and it is a real one
Removing an item from an array while you are looping forwards through it makes the loop skip the next item, because everything shuffled down a place while the counter went up. Two pods stacked together, and only one gets collected. There are two standard fixes: loop backwards through the array, or mark pods as collected during the loop and remove them afterwards. Pick one and be able to explain why it works.
Stuck?

Can't get the "at least 90 pixels from the core" rule working? Do it in the simplest way: pick a random spot, measure the distance, and if it's too close, pick another one. A while loop is the natural tool but a simple "try, check, try again" with a loop of a few attempts is completely fine at this stage.

Collision "not working"? Draw the two boxes you're testing as thin outlines so you can see the hitboxes. Nine times out of ten the picture shows you a wrong width or a wrong corner immediately.

Everything vanishes at once when you touch one pod? You're probably emptying the array instead of removing one item, or your overlap test is returning true for everything — check the direction of your comparisons.

Done when eight pods appear away from the core, the tug collects them one at a time with the score rising by ten each time, and clearing the last one instantly spawns a fresh set with the wave number going up.

STAGE
5

The rock field: velocity and bouncing

Session 9Session 7Session 6
Goal: three rocks drifting around the sector, bouncing cleanly off all four walls.
  1. Write randomBetween(min, max) and use it inside makeRock(), which returns a new rock object: a random position, a random radius between 12 and 26, a random velocity in both directions, and unstable: false.
  2. Fill a rocks array with the starting number of rocks using a loop.
  3. Write moveRocks(): loop through them, add each rock's velocity to its position, then check the four walls and reverse the right velocity when it hits one.
  4. Draw every rock with a loop and your drawCircle helper.
⚠️ A circle's edge is not its x
For a rectangle, x is a corner. For a circle, x is the centre. So a rock's left edge is x - r and its right edge is x + r. Forget it and every rock will sink halfway into the wall before turning around, which looks broken in a way that's oddly hard to spot.
💡 Make sure no rock gets a velocity of zero
A random number between −2.5 and 2.5 can come out at almost exactly zero, and you'll get a rock that just sits there like it's asleep. Decide how you'll prevent that. There's more than one reasonable answer.
Stuck?

A rock gets stuck vibrating against a wall? That's the classic. Flipping the velocity fixes the direction but doesn't fix the position — the rock is still overlapping the wall next frame, so it flips again, and again. The fix is to also push it back to exactly touching the wall when you flip. Say the fix out loud: "flip the velocity, then fix the position."

All your rocks are identical? You've probably called makeRock() once and pushed the same object in several times. Each push needs its own fresh call.

Done when three different-sized rocks drift at different speeds and angles, and every bounce happens exactly at the wall — not sunk into it, not bouncing off thin air — with nothing ever getting stuck.

STAGE
6

Rocks hit the core: circle collision and consequences

Session 12Session 11Session 6
Goal: the game now has stakes. Rocks reaching the core cost you shield, and running out ends the run.
  1. Write circlesOverlap(a, b) using your distance() function — two circles touch when the gap between their centres is smaller than their two radii added together.
  2. Write checkCoreHits(): loop the rocks, test each against the core, and on a hit take shield away — one normally, three if that rock was unstable.
  3. Remove the rock that hit and spawn a fresh one, so the field never runs empty. (Watch out for the same remove-while-looping trap from Stage 4.)
  4. Draw the shield number inside the core so the player can see the damage happening.
  5. When the shield reaches zero, or the timer reaches zero, set gameOver to true. Draw an end screen with the final score and the reason it ended, plus "Press R to fly again".
🎯 Notice what you just reused
The distance formula you wrote for a mouse click in Session 11 is now deciding whether a rock hit a space station. Same three lines, completely different job. That's the whole point of writing functions.
Stuck?

Shield dropping by five at once instead of one? Your rock is overlapping the core for several frames in a row and being counted each frame. Removing the rock the moment it hits is the fix the spec asks for — make sure you're actually removing it, not just scoring it.

Game-over screen flashing then disappearing? Your draw function is still painting over it, or resetGame() is being called somewhere it shouldn't. Remember the guard from Stage 2: when the game is over, update should be doing nothing.

Done when you can sit and watch the shield tick down from rock hits, the run ends properly at zero, and R starts a completely clean game — score back to zero, shield full, timer at 60, one wave of pods, three rocks.

Unstable rocks and the mouse

Session 11Session 6Session 7
Goal: the second half of the game. Your right hand gets a job.
  1. Every 5 seconds of game time, pick a random rock from the array and set its unstable flag to true. Use your frame counter to decide when.
  2. Draw unstable rocks in a clearly different colour so the player can spot one instantly.
  3. Write getMousePos(event) — properly, with the page-position conversion — and add a click listener on the canvas.
  4. On a click, loop the rocks and find the one containing the click point (distance from the click to the rock's centre, versus its radius).
  5. Branch on the boolean: unstable rock → score up and replace it with a fresh normal one. Normal rock → score down. Empty space → nothing at all.
  6. Make sure the score can't go below zero.
⚠️ The bug that will absolutely get you
If your clicks land offset from where you actually clicked, you skipped the conversion from window coordinates to canvas coordinates. You've seen this one before. It will look like your hit test is broken when your hit test is perfect.
Stuck?

Clicking one rock affects two of them? You looped every rock and didn't stop after finding a hit. Overlapping rocks can both contain the same point — decide what should happen and make the code say it.

Nothing happens on any click? Check the listener is on the canvas, and print the converted coordinates to the console — if those numbers look sensible for where you clicked, the problem is in the distance test, not the mouse code.

Every rock turns unstable at once? Your "every 5 seconds" check is true for a whole second's worth of frames, or you're looping all rocks instead of picking one.

Done when a rock turns orange every five seconds, clicking it vaporises it for points, clicking a normal rock costs you points, clicking empty space does nothing, and clicks land exactly where you aimed even after scrolling the page.

Difficulty, polish, and the clean-up pass

Session 5Session 3All of it
Goal: turn a working program into a finished game — and then tidy the code as if someone else has to read it.
  1. Difficulty ramp: every time a wave is cleared, add one more rock to the field. The game should get noticeably nastier by wave three.
  2. Polish the page in CSS: a proper title, a controls line the player can actually read, comfortable spacing, and a colour scheme you like. It should look like something you'd show someone.
  3. Feedback: make damage visible. Flash the core, or shake it, or turn the shield number red when it's low. Your choice — but the player must feel it.
  4. The clean-up pass. Read your whole file top to bottom and fix these four things: any repeated code that should be a function; any magic number that should be in the settings block; any function longer than about 20 lines; any variable with a lazy name like x2 or thing.
  5. Add a short comment above each function saying what it does in one line. Not what every line does — what the function is for.
  6. Final check: open DevTools and play a full round. Zero errors and zero warnings in the console.
🔑 The clean-up pass is not optional decoration
This is the stage that separates "I got it working" from "I can build software". Working code that nobody can read — including you, in two weeks — is only half-finished. Every professional does this pass. Give it the full twenty minutes it deserves.
Done when you can hand the folder to someone who's never seen it, and they can open index.html, understand the controls without asking you, play a full 60 seconds, lose, and press R to go again — with a clean console the whole time.

FINAL
✓

Prove it works: the self-test

Do this before you hand it in
Goal: try to break your own game before your teacher does. Every one of these must behave.
  1. Hold two arrow keys at once. Does it fly diagonally?
  2. Fly hard into each of the four corners and hold. Does any part of the tug leave the screen?
  3. Let it run untouched for a full 60 seconds. Does it end cleanly, once, without piling error messages into the console?
  4. Press R in the middle of a game, at the game-over screen, and while paused. Does it always give a clean fresh start?
  5. Pause and then try to play. Is everything genuinely frozen — rocks, timer, tug, clicks?
  6. Scroll the page down a little, then click a rock. Does the click still land where you aimed?
  7. Collect two pods that are sitting right next to each other. Do both get collected?
  8. Clear a whole wave. New pods, wave number up, bonus scored, one extra rock?
  9. Click a normal rock ten times in a row. Does the score go down and stop at zero rather than going negative?
  10. Change one number in your settings block — the tug's speed — and reload. Did the game change, and did nothing break?
💡 Number 10 is the sneaky one
If changing one setting doesn't change the game, you've got that value hardcoded somewhere further down the file too. That's exactly the kind of thing this test is designed to catch.

🚀 Level 2 — only if the main build is finished

Genuinely optional. Pick one or two that appeal to you; don't try to do all six.

  1. Rock-on-rock collisions. When two rocks touch each other, both bounce. Every rock has to be tested against every other rock — which needs a loop inside a loop. Warning: harder than it sounds, and very satisfying when it works.
  2. Drifting pods. Give pods a slow velocity so they float too. Suddenly collecting them takes actual skill.
  3. Best score. Keep a bestScore variable and show "NEW BEST!" on the end screen when it's beaten. (It resets on reload — saving it properly comes later in the course.)
  4. Play it on a phone. Swap your mouse listener for a pointer event so tapping works too. Then work out how someone with no keyboard could steer the tug — that's a real design problem, and there's no single right answer.
  5. Warning ring. Draw a faint circle around the core showing the danger zone, and make it pulse when any rock gets close. Uses the distance function yet again.
  6. Combo scoring. Collect three pods within two seconds and score double. You'll need to remember when the last pod was collected.

Oral questions — ask these while they demo it

The demo matters less than these answers. A student who can't explain their own code has copied it from somewhere.

  1. "Show me a function that returns something, and tell me who uses what it returns."
  2. "Why is the tug's right-hand limit not just the canvas width?"
  3. "You use distance() in three places. Name all three."
  4. "What would happen if you deleted the line that clears the canvas? Guess first, then try it."
  5. "Why is a rock's left edge x - r but a pod's left edge is just x?"
  6. "Walk me through what happens, in order, in one single frame."
  7. "Which of your variables are const and why couldn't the score be one?"
  8. "Two pods are touching each other. What did you have to do so both get collected?"
  9. "If clicks landed 40 pixels off, where would you look first?"
  10. "Show me a piece of this code you're not happy with, and tell me what you'd do with another hour."
Traps deliberately left in the spec (and what they'll look like)
  • Splice-while-looping (Stage 4 & 6). Symptom: adjacent pods where only one collects; occasionally a rock survives a core hit. This is the single most valuable bug in the project — let them hit it. The spec warns them it exists but not how to fix it.
  • Circle edges on the wall bounce (Stage 5). Symptom: rocks sink halfway into the wall. Very common, easy to see once you point at it.
  • Sticky rock at a wall. Symptom: one rock vibrating in place. The fix — flip the velocity and correct the position — is the same one Pong needs in Session 13, so this is deliberate preparation.
  • Zero velocity rock. Symptom: a rock that never moves. Flagged in the spec as a design decision rather than a bug, so they have to reason about randomness rather than just be told.
  • Multi-frame core damage. Symptom: shield dropping by 4 or 5 on one hit. Teaches that a collision lasts many frames unless you remove or move something.
  • Mouse offset. Symptom: clicks miss consistently. Most likely to appear only when they scroll — worth having them scroll during the demo.
  • Magic numbers. Symptom: changing the settings block does nothing. Caught by self-test #10.
Pacing and support
  • Two weeks, four sessions. Suggested split: Stages 0–2 in the first session, 3–4 in the second, 5–6 in the third, 7–8 plus the self-test in the fourth. Homework between each is the next stage attempted alone.
  • Do not debug for them. Ask "what did you expect to happen, and what happened instead?" then "how could you see what's actually happening?" Drawing hitboxes and printing to the console solve most of this project's bugs.
  • If they're drowning at Stage 4 or 5, the shortest recovery is to have them rebuild that one mechanic in a blank file with nothing else in it. Arrays plus collisions plus a game loop all at once is a lot; isolating it usually unblocks them in ten minutes.
  • If they finish early, push them at Level 2 item 1 (rock-on-rock). The nested loop is the natural next step in difficulty and previews the thinking Breakout will need.
  • Protect Stage 8. Students want to stop the moment it works. The clean-up pass and the self-test are where the professional habits form, and they're the first thing to get skipped. Mark them as part of the grade — they're worth 20 points between them — and say so up front.

Good luck, pilot.
